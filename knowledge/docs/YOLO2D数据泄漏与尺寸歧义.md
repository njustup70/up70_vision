# YOLO2D 的两个真问题：指标虚高、top/block 尺寸歧义

> 2026-11-01 实测记录。结论先说：
> **0.96 的 P/R/mAP 不能当泛化指标**——test 里有相邻帧跨集；**top/block 也不能只看颜色或绝对像素大小**——
> 89 个 test top 里有 51 个的高度落在 block 的尺寸区间内。下面给出证据、协议和可落地的判定方案。
>
> 复现：`PYTHONPATH=. python lab/audit_split.py --data data/yolo_real_v2`

---

## 一、指标为什么虚高

### 1.1 直接证据：相邻帧跨了 train/test

`lab/audit_split.py` 在 `data/yolo_real_v2` 上跑出来（32×32 灰度余弦）：

| 检查 | val vs train | test vs train |
|---|---|---|
| 最大相似度 | **0.955** | **0.971** |
| 中位相似度 | 0.614 | **0.814** |
| ≥0.90 的帧 | 4 / 36 | **13 / 36（36%）** |
| ≥0.95 的帧 | 1 / 36 | 1 / 36 |

相邻帧跨集（同组、帧号差 ≤5、相似度 ≥0.90）**8 对**，例如：

```
test g6far_frame_0121  <->  train g6far_frame_0120   Δ帧 +1  相似 0.971
val  g6far_frame_0097  <->  train g6far_frame_0098   Δ帧 -1  相似 0.955
test g6far_frame_0021  <->  train g6far_frame_0020   Δ帧 +1  相似 0.905
```

这不是"同一场景的不同角度"，是**连拍里的相邻帧被切到了两边**。模型在 test 上只要"记住"train 的
背景/摆位就能拿高分。

### 1.2 根因：split 的三个设计问题

1. **组内分层，而不是整组留出**。`split_dataset.py` 让 6 个采集组**各自**出 val/test，
   于是 g1~g6 每一组都同时出现在 train 和 test——test 的背景、光照、物块摆位和 train 同源。
   这对"同分布随机划分"是对的，对"比赛新场地"是错的。
2. **连拍串用贪心聚类，不保证传递**。`cluster()` 把新帧和"簇中心之和"比余弦，A 像 B、B 像 C
   不代表 A 和 C 会被并进同一串；相邻帧理论上可能落到不同串、进而跨集。当前这 8 对泄漏
   是聚类造成的，还是划分后又手工搬过帧，仓库里没有记录，无法追溯；但**结果**是确定的。
3. **test 太小且被一组主导**。36 张 / 168 框，`g6far` 一组就占 123 框（73%）。
   整体 mAP 基本是"远景组 mAP"，g3 只有 8 框、g5 只有 7 框，单组数字没有统计意义。

### 1.3 去掉近重复后，真实水平大概是多少

把 test 里"和 train 最大相似度 ≥ 阈值"的帧删掉，再评同一个 mix4 模型（conf 0.45）：

| test 过滤 | 图片数 | P | R | F1 | 备注 |
|---|---|---|---|---|---|
| 不过滤 | 36 | 0.964 | 0.958 | **0.961** | 现在对外报的数 |
| 去掉 ≥0.90 | 29 | 0.951 | 0.943 | 0.947 | 变化不大（被删的多是易例） |
| 去掉 ≥0.85 | 20 | 0.950 | 0.905 | 0.927 | 开始露底 |
| 去掉 ≥0.80 | 18 | 0.935 | 0.878 | **0.905** | g6far R 掉到 0.75 |

按采集组算宏平均（6 组等权）：**macro R ≈ 0.908**，最差两组 `g3tilt` R 0.75、`g4stack` R 0.78。
也就是说：**0.96 是"同场景同分布"的数；换场景前，合理的预期是 0.88~0.91**，而且斜视/叠放组更差。

> 不要用"删掉难例后 F1 还很高"来自我安慰：删掉的是**近重复**，留下的才是真正没见过的帧。
> 真正该做的是重新划分，而不是在原 test 上挑帧。

## 二、怎么把评测做真

### 2.1 重新划分：按"场次"留出，不按帧分层

推荐优先级从高到低：

1. **整场次留出（首选）**：一个采集场次（同一天/同一房间/同一光照/同一套摆位）只能进一个划分。
   train = 场次 A/B/C，val = 场次 D，test = **没参与过任何调参的场次 E**。
2. **时间块切分**：同一场次内按连续帧块（如每 20 帧一块）分配，块间强制最小间隔
   （≥30 帧或 ≥30 s），保证相邻帧绝不跨集。
3. **连通分量聚类**：相似度图取连通分量（而不是贪心中心），阈值取 0.92~0.95；
   自检必须打印"跨集最大相似度"，>0.90 就拒绝出报告。
4. **外部 test**：新房间/新光照/新摆位，至少 50 张、按距离和角度分层。
   这是唯一能回答"比赛场地行不行"的集合；现有的 248 张同走廊数据做不到。

### 2.2 报告口径

- 同时报 **总体 + 每组 P/R + macro R + 最差组**；只报总体会被 g6far 掩盖。
- 报"去重后 test"和"外部 test"两个数；原 test 只用于和旧模型做同口径对比。
- **test 只测一次**；调 conf、选模型、改后处理都只看 val。
- 数据量允许时做 **leave-one-group-out**：每次留一个采集组，训练 3~6 个模型，报均值±方差。
  CPU 上 40 epoch 约 25~40 分钟/次，至少留 `g4stack`（叠放）和 `g6far`（远景）各做一次。

### 2.3 v3 已重建（2026-11-01）

用 `lab/rebuild_split.py` 按**整组留出**重建了 `data/yolo_real_v3`：

| 划分 | 采集组 | 图 | 框 | block/top |
|---|---|---|---|---|
| train | g1front + g2top + g6far | 181 | 789 | 366 / 423 |
| val | g5dist | 15 | 52 | 29 / 23 |
| test | g3tilt + g4stack | 52 | 173 | 94 / 79 |

选择理由：

- test 用 **g3tilt + g4stack**：v2 上这两组 R 只有 0.75 / 0.78，是最能暴露问题的两组；
- val 用 **g5dist**：距离梯度，适合调 conf，且与 test 不重叠；
- g6far 放 train：它是唯一的大规模远景组（646 框），留作 test 会让训练集只剩 368 框；
- **代价**：v3 的 test 不测远景泛化。远景另建一折：

```bash
# 远景留出折（train=g1~g4，val=g5，test=g6far）
PYTHONPATH=. python lab/rebuild_split.py --out data/yolo_real_v3_far \
  --train-groups g1front,g2top,g3tilt,g4stack --val-groups g5dist --test-groups g6far
```

审计结果（`lab/audit_split.py`）：

```text
val  vs train  最大相似度 0.506   ≥0.90 的 0 张
test vs train  最大相似度 0.661   ≥0.90 的 0 张
相邻帧跨集 0 对
✅ 审计通过
```

对比 v2：test max 0.971、8 对相邻帧跨集；v3 的跨集相似度已经降到 0.66，**train/val/test 没有任何一组重叠**。

**v3 基线训练结果（2026-11-01，从 COCO 起 40 epoch）**：

| 划分 | 图/框 | P | R | mAP@0.5 | mAP@0.5:0.95 |
|---|---|---|---|---|---|
| val（g5dist） | 15 / 52 | 0.881 | 0.792 | 0.884 | 0.587 |
| **test（g3tilt + g4stack）** | **52 / 173** | **0.813** | **0.824** | **0.850** | **0.577** |

分组看 test：`g3tilt` R **0.681**（类别错 10）、`g4stack` R 0.898（合并 8）。
同一 test 上 mix4（训练时见过 g3/g4）F1 0.946，v3 基线 0.910——**这 0.036~0.12 的差就是泄漏/记忆的贡献**。

后续 90° 旋转增广（`v3_aug2`）把 test mAP50 提到 **0.885**、类别错 18→6、g3tilt R 0.815；
代价是 FP 3→13、合并仍 15。说明"斜视 top"可以靠旋转解决，**合并和 FP 必须靠数据**。

## 三、top/block 为什么会在 2D 侧打架

### 3.1 先看数据：尺寸区间大量重叠

test 里 GT 框高度（像素）：

| 类别 | 25% | 中位 | 75% | 90% |
|---|---|---|---|---|
| `block` | 106 | **107** | 214 | 336 |
| `top` | 59 | **97** | 105 | 213 |

**89 个 top 里有 51 个（57%）的高度落在 block 的 p10~p90 区间内**。
原因很简单：350 mm 的 block 在 2 m 外，和 200 mm 的 top 在 1 m 外，像素高度可以一样。
**没有距离，绝对像素大小不可能分开 top/block**——这不是模型不够好，是信息不足。

### 3.2 颜色也不是可靠判据

- test 的 89 个 top 里，**14 个只看到一种颜色/颜色很弱**（侧视、遮挡、过曝）；
  模型仍把其中 **13 个判成 top**，只有 1 个判成 block（`g5dist_frame_0014`，top 高 213 px、置信度 0.57）——
  说明模型**主要不是靠颜色**，但也没有稳定的尺寸依据。
- 把 test 图的红/蓝互换后，156 个匹配框里有 **6 个类别翻转（3.8%）**——
  模型确实用了一点"颜色构成"的先验，但不是决定性的。
- 把色相整体 +30° 后 R 从 0.958 掉到 0.506，灰度化后 R 掉到 0.738——
  检测本身依赖红/蓝外观（只在红蓝数据上训练过），这部分不能简单"去颜色"。
- train 里有 **6 个标成 block 的框同时含红蓝两色 ≥20%**（如 `g6far_frame_0098`），
  很可能是把 top 标成了 block，或相邻 top 的颜色漏进了框——这类标签噪声会直接教坏模型。

> 这说明：**当前数据里"单色 top 被判成 block"只出现了 1 次**，不是主要错误来源；
> 真正的问题是"模型没有稳定的尺寸依据"——现在的 13/14 有运气成分，换场景就会暴露。
> 所以先补数据/加尺寸先验，不要为了 1 个样本加一堆硬规则。

### 3.3 可落地的判定方案（按可靠性排序）

#### 方案 A：叠放相对尺寸（不需要标定，最适合塔）

塔是竖着叠的：同一个塔里，**上方框高 / 下方框高**：

- `top` 在 `block` 上：理论 200/350 ≈ **0.57**；test 里 55 对实测大多在 **0.44~0.75**；
- `block` 在 `block` 上：同距离约 **1.0**；test 里 22 对大多为 1.0（斜视/近大远小会偏到 0.49 或 5.7，需加透视容忍）。

做法：按 x 方向重叠 >0.5、上方框底边接近下方框顶边，关联成"塔"；
对每个上方框算 `h_upper / h_lower`，落在 0.35~0.80 且颜色为单色 → 判 `top`；接近 1 → 判 `block`。

**它只对"有下方参照"的塔有效**：test 的 14 个单色 top 里，只有 2 个能找到有效的下方框
（其余是孤立目标，或支撑块没被检出/没标）。所以不要把 A 当成通用解——
塔场景先做 A，孤立目标仍要走 B/C/D/E。

#### 方案 B：地面单应 → 距离 → 绝对尺寸（适合孤立目标）

物块放在地上，bbox 底边中点就是接地点。用相机内参 + 相机高度/俯仰（或标定好的地面单应）：

```
Z = fy * H / (v_bottom - v_horizon)        # 水平相机、地面高度 H
size_mm ≈ bbox_h_px * Z / fy               # 小孔近似
```

`size_mm` 对 350 / 200 取中点 275 mm 分类。距离误差 ±30% 以内都能分开（350/200=1.75）。
标定：在地面放 4~6 个已知点（或已知距离的方块），拟合 `v_bottom -> Z` 的曲线/单应；
相机固定时标一次即可。**注意**：top 若叠在 block 上，它的底边不在地面，
要先找同一塔最下面那个 block 的接地点，再把 Z 复用给上面的 top。

#### 方案 C：深度相机（最稳，建议作为最终方案）

深度侧已有链路：`size_mm = bbox_h_px * depth_mm / fy`，取框内深度中位数即可。
2D 只负责 bbox + 颜色，深度负责绝对尺寸；350 vs 200 直接分开，不再依赖颜色或塔结构。
**这是和深度同学的分工边界**：2D 不估距离，但 2D 必须把 bbox 和颜色给准。

#### 方案 D：颜色布局只做"证据"，不做"规则"

- 框内红、蓝各 ≥20% → **几乎可以确定是 top**（block 是单色）；可以作为高置信规则；
- 只看到一种颜色 → **不能反推 block**，应该输出 `ambiguous`（或让下游看尺寸/深度/下一帧）；
- 不要把"单色 = block"写死，否则侧视 top 必错。

#### 方案 E：多帧颜色融合（解决"这一帧只看到一种颜色"）

给每个框做简单 IoU 跟踪，维护每条轨迹的红/蓝累计命中率：
机器人/相机稍微动一下，top 的另一半就会露出来；**只要历史里出现过红蓝各 ≥20%，就锁定 top**。
这比单帧判色稳，且不需要深度；实现量约 50 行（IoU 关联 + 计数器）。

#### 方案 F：训练侧修正（和 A~E 并行）

1. **标签按物理尺寸标，不按颜色标**：单色侧视的 top 也要标 `top`；
2. **清掉 6 个"双色 block"疑似错标**，或逐张复核；
3. **补 hard examples**：单色 top、蓝上红下/红上蓝下、半遮挡、边缘截断、远景 40~80 px；
4. **加强颜色增广**：`hsv_h=0.5`（现在是 0.015）、`hsv_s=0.9`，让模型别把"某种红/蓝"当类别；
5. 训练/部署都用 **480 或 640 保持一致**；远景小目标别用 416；
6. 如果 A~F 后仍混淆，再做**二阶段分类器**：输入裁剪框 + 塔内相对高度 + 颜色布局，
   用逻辑回归/GBDT 就够（样本少，别上大网络）。

### 3.4 判定表（建议直接照这个实现）

| 框内红蓝 | 塔内相对高度 | 有距离/深度 | 判定 |
|---|---|---|---|
| 两色各 ≥20% | 任意 | 任意 | `top`（高置信） |
| 单色/弱色 | 上方框/下方框 ∈ [0.4, 0.8] | 无 | `top`（方案 A） |
| 单色/弱色 | ≈1.0 | 无 | `block` |
| 单色/弱色 | 无参照 | 有 | `size_mm` 近 200 → top；近 350 → block |
| 单色/弱色 | 无参照 | 无 | `ambiguous`（不要硬判 block） |

## 四、验收指标（下一版模型/规则按这个验）

1. **去重 test / 外部 test**：F1 ≥ 0.90，且 macro R ≥ 0.90；
2. **单色 top 子集**（现在 14 张）：top recall ≥ 0.95，不允许再出现"单色 top → block"；
3. **叠放组 g4stack**：R 从 0.78 提到 ≥0.90；
4. **斜视组 g3tilt**：R 从 0.75 提到 ≥0.90；
5. 原 v2 test 作为"同口径回归"保留，但不再作为对外指标。
