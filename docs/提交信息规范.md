# Git 提交信息规范（v1，2026-10-17）

> 一句话：`git log` 是给人扫读的，标题说明白"改了什么"，正文只补原因和验证。
> 详细过程、实测数据、踩的坑记在 `docs/progress.md`，不进提交信息。

---

## 1. 标题（第一行）

格式：`<type>: <做了什么>`（与 `docs/视觉组协作规范.md` §1 一致）

- `type` 只用三个：`feat` / `fix` / `docs`
- 动词开头，说结果：新增 / 修复 / 改为 / 删除
- **不超过 50 个字符**，结尾不加句号
- 不写：文件名清单、测试数量、任务单名、`(#5)`（GitHub squash 时自动加）、
  `(m8)` 这类内部代号
- 中文与英文/数字之间留空格

| 写法 | 示例 | 问题 |
|---|---|---|
| ❌ 改前 | `feat: 真 ArUco 检测核心（飞书任务一）— aruco.py / gen_aruco.py / assets/aruco + 14 项测试 (#5)` | 61 字，文件、测试数、任务名全塞进来 |
| ✅ 改后 | `feat: 新增真 ArUco 检测器，按契约返回 ArucoMarker` | 一句话说清加了什么、输出是什么 |

---

## 2. 正文（可选，最多 4 行）

标题下空一行再写，每行 ≤ 80 字符，只写三样：

1. **为什么改**（一句话；看标题就懂的可以省）
2. **影响面**：契约 / 配置 / 依赖，一句
3. **怎么验证**：命令 + 关键数字，一句

本仓库只有两种验证命令（镜像里没装 pytest）：`python tests/test_*.py`（回归，共 36 项）、
`python scripts/demo.py` + `python scripts/check_env.py`（冒烟）。写成 `pytest -q` 等于没写——跑不起来。

```text
feat: 新增真 ArUco 检测器，按契约返回 ArucoMarker

- 用 OpenCV 的 aruco 模块实现；无码返回空列表、按 id 升序
- detector.name 多一个可选值 aruco，默认仍是 blob
- 验证：9/9 张真值图通过，四角误差 ≤ 0.25 px；36 项回归全过
```

不写这些：

- 按文件罗列（`- README: ...`、`- progress.md: ...`）——那是 `git show` 的活
- 重复标题，或把每个子提交的标题都粘进来
- 过程流水账（第一版怎么做、后来怎么改）
- 未展开的缩写（`m8`、`坑 34`）

---

## 3. 什么时候写正文

| 情况 | 正文 |
|---|---|
| 只改文档 / 注释 | 不写 |
| 改行为、配置、依赖 | 写 1~3 行 |
| 动契约 | 加一句"契约：改了 X，见 `docs/interface.md` 2.2" |
| 修 bug | 加一句"原因 + 影响范围" |

## 4. 完整例子：一条从零写出来的提交

任务二做完，`main` 上应该只留下这一条（标题 31 字，正文 3 行）：

```text
feat: 新增 ArUco 实时循环，支持窗口与无头两种跑法

- 循环只做四件事：取帧 -> 检测 -> 画框 -> 输出，终端每 0.5 s 报一行帧率
- 新增 scripts/run_aruco_live.py；配置加 live.* 五个字段，默认不落盘
- 验证：容器内 --headless 跑 300 帧无报错；36 项回归全过
```

逐行对照：

| 行 | 内容 | 满足哪条 |
|---|---|---|
| 1 | `feat:` + 一句话说清加了什么 | §1：动词开头、≤ 50 字、不带文件清单与测试数 |
| 3 | 改了哪块行为 | §2：影响面（行为一句） |
| 4 | 新增文件 + 配置字段 | §2：影响面（配置一句，说清旧配置不受影响） |
| 5 | 命令 + 环境 + 数字 | §2：怎么验证 |

写进 git（有正文用 heredoc，`-m` 里的换行容易丢）：

```bash
git commit -F - <<'EOF'
feat: 新增 ArUco 实时循环，支持窗口与无头两种跑法

- 循环只做四件事：取帧 -> 检测 -> 画框 -> 输出，终端每 0.5 s 报一行帧率
- 新增 scripts/run_aruco_live.py；配置加 live.* 五个字段，默认不落盘
- 验证：容器内 --headless 跑 300 帧无报错；36 项回归全过
EOF
```

只改文档就省掉正文，一行收工：

```text
docs: 新增代码注释规范，写清四层注释与自检项
```

squash 合并时，在 GitHub 的提交信息框里**整段替换**成上面这块，别用它自动生成的子提交列表。

## 5. squash 合并后的提交信息

仓库只允许 squash 合并，**`main` 上留下的这一条就是唯一记录**，所以：

- 标题用 PR 标题；正文写合并后的**结果**，不是各子提交的拼接
- 删掉 `* feat(m8): ...`、`* docs(m8): ...` 这类子标题
- 别按文件列；按"检测器 / 配置 / 文档"这种模块或行为分组，最多 4 行
- 中间过程、实测矩阵、坑 → `docs/progress.md`

## 7. 提交前自检（5 条）

- [ ] 标题 ≤ 50 字，一句话，没有文件清单 / 测试数 / 任务名
- [ ] 正文 ≤ 4 行，只写原因 / 影响 / 验证
- [ ] 没有重复标题，没有按文件罗列
- [ ] 缩写已展开，数字带条件（环境 / 分辨率 / 帧数）
- [ ] 细节已记进 `docs/progress.md`（如果有）

---

## 8. 各文档分工

| 文档 | 放什么 |
|---|---|
| 提交信息 | 结论：改了什么、为什么、怎么验 |
| `docs/progress.md` | 细节：实测数据、过程、坑、未验证项 |
| `docs/interface.md` | 契约条目 |
| `docs/代码注释规范.md` | 代码里的注释与 docstring |
