# 视觉组协作规范 v1.1

> 适用范围：UP70 战队视觉组仓库（2 人），全流程 Ubuntu + Docker（环境约定见仓库 README）。本规范的目标只有三条底线：**main 永远能跑、每行代码有人负责、AI 代码可追溯。**
> 制度从简，执行从严。有分歧先改文档，再按新文档执行。

## 1. 分支模型

- **main 分支受保护**：禁止直接 push，禁止 force push，一切变更通过 PR 进入。
- **工作分支**：命名 `<type>/<中文关键词>`，type 用第 2 节词表。
  - 例：`docs/阶段一资料`、`feat/pnp-复现`、`fix/qr-丢包`。
- 分支生命周期**不超过一周**；超期说明任务切分过大，必须拆分。
- 不设 dev、release 等其他长期分支。

## 2. 提交规范

格式：`<type>: 中文一句话说清做了什么`

| type | 含义 |
|---|---|
| feat | 新功能 |
| fix | 修 bug |
| docs | 文档 |
| refactor | 重构（不改行为） |
| test | 测试相关 |

- 一次提交只做一件事。
- 禁止 `update`、`修改`、`1` 等无信息量的提交说明。
- 例：`feat: 新增 ArUco 角点检测`、`fix: 修正外参单位换算`、`docs: 补全阶段一资料`；反例：`docs: 更新若干文件`。

## 3. PR 与评审

- **谁的域谁实现，对方评审，无例外。**
- PR 描述必须包含四要素：
  1. 做了什么；
  2. 怎么验证的（用了什么数据、什么结果）；
  3. AI 生成了哪些段落；
  4. 是否改动接口契约（动了要单独说明）。
- **合并硬条件：reviewer 按 `docs/interface.md` 中该模块登记的运行方式跑通**（登记三项：运行平台 / 一条启动命令 / 看到什么算通过；涉相机的模块登记设备透传与显示方式）。只看 diff 通过不算审过。
- **合并者当天在 main 上跑一遍冒烟**（`demo.py` / `check_env.py`），失败立即 revert——两个各自通过的 PR 同天进 main 仍可能冲突，stub 换真实现那次合并尤其危险。
- 采用 **squash 合并**：一个任务压缩为一个提交进入 main，保证 main 历史一任务一提交。
- 改一行也走 PR。省下的五分钟换不回 main 崩掉的代价。

## 4. AI 代码条款

1. AI 生成的段落必须在 PR 描述中标注。
2. 作者必须能逐行解释自己提交的任何一行代码，包括 AI 生成的部分。
3. reviewer 有权当场要求作者解释任意一行；解释不出来即打回。
4. **标注必须落进 git 历史**：提交信息强制带 `Ref: PR #N`，AI 使用情况在 `docs/pr-log.md` 各记一行（日期 / PR 号 / 用 AI 做了什么 / 是否复核）。squash 后 PR 描述不会留在 git 历史里，不落盘的标注等于没标注。

本条的目的：防止"代码在仓库里、理解不在脑子里"。

## 5. 大文件与数据

- 权重（`*.pt`、`*.onnx`）、数据集、rosbag **一律不进 git**。
- `.gitignore` 建仓第一天配置：`*.pt`、`*.onnx`、`*.bag`、`data/`、`runs/`。
- 大文件放共享网盘，**文件名附带合并进 main 后的提交短哈希**（例：`yolo11n-a3f2c1d.pt`），README 中登记链接。不要用工作分支的哈希——squash 后它不存在于 main，一个月后对不上。保证任何时刻代码版本与权重版本可对应。

## 6. 标签与回滚

- 每次**合跑日**打标签：`run-YYYYMMDD`，含义为"该时点整套系统经联调验证可运行"。
- 调试期出现问题时，`git checkout run-YYYYMMDD` 回滚到最近的可运行版本。
- 比赛前的版本必须打正式标签（如 `v-comp-1`）。

## 7. 接口契约

- 契约内容：topic 名称、消息类型、坐标系约定（`base_link` / `camera_link` / `lidar_link`）、外参配置文件格式。
- 契约文档位置：`docs/interface.md`，单独维护。
- 任何改动必须在 PR 中声明，并经对方同意后方可合并。

## 8. 每周节奏

- **每周 15 分钟两人小会**，只谈三件事：上周完成 / 当前卡点 / 下周计划。
- **每周合跑一次**：两条线的代码在 main 上联调，当天打 tag。
- **评审回应不超过 24 小时**：哪怕一句"今天没空，明天中午前看"，也不让 PR 干等——两人团队死于互相等，不是死于代码冲突。审不动对方算法就审三样：命令能复现、契约字段一致、自己看得懂。
- **踩坑笔记**：记入 `progress.md` 第五节（沿用仓库现有约定），格式为现象 / 原因 / 处理。本笔记即无学长条件下的经验传承，下届直接继承。

## 9. Owner 制

- 每个模块**有且只有一个 owner**，另一人为 reviewer。
- owner 负责实现、日常维护、出问题时修复；reviewer 有知情权与建议权，无实现义务。
- 两人都要能"只读跑通"对方的最简流水线（能看懂、能重启），防止单点故障。
- 当前分配（复现期，后续随分方向正式化）：
  - YOLO 与 2D 处理侧 owner：________
  - PnP 与几何/点云侧 owner：________

## 10. 旧仓库处理

- 旧仓库归档并设为只读，新仓库开发。
- 复现时只参照旧仓库的**数据与流程文档**，不照搬代码实现；旧代码跑不通属预期内，不算失败。

## 11. 制度预算

以上是全部规矩，以此为上限：

- 规则总量不超过一页；**新增一条，必须同时删除或合并一条旧的**。
- 每条规则必须能一句话说出"它防的是哪次具体事故"，说不出来的就是装饰，删。
- 每月合跑日复审一次制度，整月没触发过的规则自动降级为"建议"。
- 制度只活在这一份文档里，不散落在聊天记录中。

## 附：环境问题时间盒

任何环境、驱动、依赖问题，卡住**超过两天**即启动降级：换版本、换设备、绕过，先保证链路通，后追求完美配置。卡住的坑记入 `progress.md` 第五节。
