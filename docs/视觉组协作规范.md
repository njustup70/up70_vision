# 视觉组协作规范 v1.2

> 适用范围：UP70 战队视觉组仓库（2 人），全流程 Ubuntu + Docker（环境约定见仓库 README）。
> 目标三条底线：**main 永远能跑、每行代码有人负责、AI 代码可追溯。**
> 制度从简，执行从严。**本规范只有 6 条，加新规则之前先读第 6 条。**
> 有分歧先改文档，再按新文档执行。

---

## 1. 一切变更通过 PR 进 main

**防的是**：赶时间直推 main，把别人正在跑的东西搞坏。

**怎么做**

- 在 GitHub 仓库设置里开 main 分支保护。**这条靠设置，不靠自觉。**
- 分支名 `<type>/<中文关键词>`，type 只用三个：`feat` / `fix` / `docs`。
  例：`feat/pnp-复现`、`docs/阶段一资料`。
- 仓库设置里只允许 **squash** 合并 —— 一个任务在 main 上压成一条提交。
- 合并时把提交信息写成 `<type>: 中文一句话 (#PR号)`。
  **PR 描述不进 git 历史，这条提交信息是唯一留下的记录**，别直接点确认。
- squash 合并后留在 git 历史里的提交信息怎么写，见 `docs/提交信息规范.md`。
- **合并由 PR 作者自己按**：评审回「过」之后作者点合并，他知道自己的改动何时合得进去。
  作者当天不在，reviewer 代按，提交信息里署原作者名。
  不设「合并负责人」—— 绑人就会多出「等他来按」的等待，两人团队死于互相等。
- **合并后当天，在 main 上跑一遍冒烟**（`python scripts/demo.py` 与 `python scripts/check_env.py`）。
  失败先停下定位，确认是本次合并引入的再 revert。
  防的是：两个各自通过的 PR 同天进 main 仍可能冲突。
  第 4 条那次跑的是分支（旧 main + 他的改动），这次跑的是组合态（他的 + 你的），两者不能互替。

**例子**

```
✅ feat: 新增相机输入源 (#2)
❌ Docs/阶段一资料 (#1)      ← 缺 "docs: " 前缀；写的是分支名，不是"做了什么"
```

> 附带：权重（`*.pt` / `*.onnx`）、数据集、rosbag 一律不进 git。
> 忽略规则见仓库根 `.gitignore`，本规范不重复维护一份。

## 2. 接口契约写在 `docs/interface.md`

**防的是**：两个人各写各的，合到一起对不上 —— 而且**不报错**，只是结果不对。

**什么是契约**：凡是被两方以上依赖、**改它会牵连对方写法**的数据结构与函数签名。
阶段一是 `detect()` 的签名与返回结构；等接了 ROS，话题名与消息类型也算。

**怎么做**：改契约的 PR，描述里必须写一句"**动了契约，动的是哪一条**"，并等对方同意再合。
不属契约的改动（画成什么样、命令行长什么样）不用等同意。

**例子**

```
✅ PR 描述：动了契约 —— detect() 的返回由 list[dict] 改为 list[ArucoMarker]，
   它决定搭档 aruco.py 怎么构造返回值，请确认
❌ 直接把 center 从 (int, int) 改成 (float, float)，谁都没说
```

## 3. AI 生成的代码，作者必须能解释

**防的是**：代码在仓库里，理解不在脑子里 —— 出问题时谁都修不了，只能重写。

**怎么做**

- PR 描述里写明哪些段落是 AI 生成的。
- 合并前，作者要能**逐行说出这行在干什么**。
- 评审时看不懂就当场问。答不上来不算过。
- 注释写到什么程度见 `docs/代码注释规范.md`：要写「为什么、边界、写错的症状」，复述代码的注释一律删掉。

**例子**

```
✅ PR 描述：stub_aruco.py 的六个场景由 AI 起草，人工核对了角点顺序与排序逻辑
❌ PR 描述："用 AI 写的，能跑" —— 被问"move 场景的行程为什么多留两个码宽"时答不上来
```

## 4. 评审：拉到自己机器上跑一遍

**防的是**：只看 diff 点同意，结果全是"看起来对"。

**作者要做的（写进 PR 描述）**

- **一条能直接复制的启动命令**
- **看到什么算通过** —— 写具体数字，别写"正常运行"（仓库已有这条约定：断言带具体数字）

**评审要做的（三样，缺一不算审过）**

1. **拉下来跑一遍**

   ```bash
   git fetch origin
   git switch <他的分支名>
   # 按他给的那条命令跑
   ```

   **跑出任何错 —— 报错、结果不对、和他写的对不上 —— 立刻在 PR 里回一句。**
   不要攒着：你的意见是他继续往下写的依据，攒一天的代价是他在错的基础上多写一天。

2. **契约字段一致** —— 对照 `docs/interface.md` 看字段名、类型、顺序
3. **自己看得懂** —— 看不懂就问，别装作看懂了

**发现问题只提，不要动手改对方的分支** —— 谁的域谁实现，改是他的事。

每个模块**有且只有一个 owner**（另一人是 reviewer）；两人都要能"只读跑通"对方的最简流水线。

**没写完的 PR 先标成 Draft**，不要让人白跑。
**24 小时内给回应** —— 哪怕一句"今天没空，明天中午前看"。两人团队死于互相等，不是死于代码冲突。

**例子**

```
✅ PR 描述：
   python scripts/run_aruco_live.py --source stub --scenario cycle --max-frames 180 --headless
   退出码 0；日志里 markers=0 与 markers=3 各出现过；帧号 0 → 179 连续
❌ PR 描述："跑一下就知道对不对"

✅ 评审时发现帧率只有 12，当天就在 PR 里说
❌ 发现了，想"回头再说" —— 三天后作者已经在这基础上又加了一层逻辑
```

## 5. 踩的坑记进 `progress.md` 第五节

**防的是**：同一个人踩两次，或者你踩过的坑搭档再踩一遍。

**怎么做**：就三栏 —— **现象 / 原因 / 处理**。

**例子**

```
现象：cv2.imwrite 返回 False 但不抛异常
原因：OpenCV 少数"静默失败"接口
处理：必须显式检查返回值
```

环境、驱动、依赖问题**卡住超过两天就降级**：换版本、换设备、绕过。
先保证链路通，后追求完美配置。

**例子**

```
✅ 相机在容器里打不开，折腾两天无进展 → 改用 stub 跑通全链路，相机接入单独排期
❌ 为相机权限耗掉整个阶段
```

## 6. 本规范只有 6 条，加一条必须先删一条

**防的是**：规则越加越多，最后没人记得住，全都失效。

- **条数固定为 6**：新增一条必须同时删掉或合并一条，所以条数永远不涨。
- 每条规则必须能一句话说出"**它防的是哪次具体事故**"。说不出来的就是装饰，删。
- **整月没触发过的规则，从本规范删掉**（要保留原意就移进 `progress.md`）。
- 制度只活在这一份文档里，不散落在聊天记录中。

**例子**

```
✅ 想加"提交信息必须带 Ref: PR #N" → 先问它防的是哪次事故？答不出来；
   而且它与 squash 冲突（分支内提交信息会被丢弃）→ 不加
❌ 每踩一个坑就加一条规则 → 三个月后 30 条，没人记得住，等于没有
```
