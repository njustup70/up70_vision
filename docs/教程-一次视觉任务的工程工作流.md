# 从任务书到可验收交付：一次视觉任务的工程工作流

## 文档说明

这份教程复盘一个真实任务的全过程：给一个视觉仓库加上 ArUco 位姿估计与识别效果测试，最后交付 13 个提交、11 项新测试、一份实测报告。重点不是代码怎么写，而是每一步该产出什么、什么情况下必须停下来复核、怎样才算做完。

全部内容约 60 分钟，其中包含一次动手验证。读者需要有 Python 基础，用过 `numpy` 和 OpenCV 更佳，不需要事先了解 PnP。

| 时间 | 内容 | 完成标志 |
|---|---|---|
| 0 到 8 分钟 | 五步流程与场景引入 | 能按顺序说出五步，并说出每步的产物 |
| 8 到 20 分钟 | 读现状、写计划书 | 能在自己的仓库里列出"可复用 / 缺口 / 冲突"三张单子 |
| 20 到 40 分钟 | 复核、分层实现 | 能说出三条"不报错但算错"的判据与各自的症状量级 |
| 40 到 52 分钟 | 验收、文档、动手验证 | 跑通脚本，四个数字与文中一致 |
| 52 到 60 分钟 | 自测与常见坑 | 八道题至少答对六道 |

文中所有数字都在本机实测过，环境为 Windows 11 + Python 3.10.22 + OpenCV 4.12.0 + numpy 2.2.6，仓库是 `up70_vision`。代码在 Linux 容器内同样可跑，差别只在路径分隔符。

## 一、从一个场景开始

你家要装修。你找到的施工队不是进门就砸墙，流程是固定的：先去现场量房，量完出一份图纸和报价，你审图时发现"这里承重墙不能动"，图纸改一版，然后按水电、瓦工、木工、油工的顺序分步施工，每步完工你验收签字，最后交钥匙并留一本说明书。

工程任务和装修是同构的。任务书只写了"把这面墙改成开放式厨房"，至于墙里有没有水管、哪面是承重墙、先做哪一步，都得在量房和审图阶段搞清楚。

这一步搞清楚的东西，决定了后面是返工三次还是顺利交付。本次任务里就有一处：任务书写着"位姿估计需要相机内参"，而我打开仓库发现当前分支上根本没有检测代码，那些代码在另一个分支上。如果没有量房就动手，第一天写出的代码会全部放错位置。

### 类比与术语对照

| 装修里的东西 | 这次任务里的对应物 | 术语 |
|---|---|---|
| 量房 | 读分支、读契约、读已有测试 | 现状盘点 |
| 图纸与报价 | 计划书：口径、判据、交付边界 | 技术方案 |
| 审图发现承重墙 | 用实测打假计划里的假设 | 方案复核 |
| 分步施工 | 每个提交只做一件事，可独立回滚 | 提交切分 |
| 验收签字 | 带具体数字的验收条目 | 判据 |
| 说明书 | 文档与已知坑记录 | 交付文档 |

需要提前建立警惕的一点：这次任务里最难发现的错误，全部是"程序不报错、结果却是错的"。位姿算错时终端照样打印一行漂亮的数字，重投影误差照样是 0.0 px，只有拿尺子量过、或者拿已知真值比对过，你才知道它错了。所以整个工作流的重心不在写代码，在于**先造出能判对错的东西**。

## 二、第一步不是写代码，是把现状读成三张单子

任务书是 2026-10-13 写的，开工是 10-18。五天里仓库前进了十几个提交，任务书的"当前状态"一节已经过期。读现状就是把这个差值找出来。

先看分支，不看文件内容：

```powershell
git rev-parse --abbrev-ref HEAD      # 当前在哪个分支
git log --oneline -5                 # 本分支最新提交
git log --oneline -5 origin/main     # 主干最新提交
git ls-tree -r --name-only origin/main | Measure-Object -Line
```

本次的输出很说明问题：当前在 `docs/阶段一资料`（`b69720f`），而 `origin/main` 已经到 `0c0348e`。当前分支的 `src/` 下只有 8 个空 `__init__.py`，`git ls-tree` 列出的文件数从三十几个变成十个。也就是说，**在这个分支上写位姿代码，会连它消费的检测函数都找不到**。

这一步要产出三张单子，写进计划书的第一节。

| 单子 | 本次的内容（举例） | 为什么必须写下来 |
|---|---|---|
| 可复用 | `ArucoMarker.corners_px` 已是亚像素、顺序已是 TL/TR/BR/BL；`CameraIntrinsics.from_dict` 现成；`undistort_points()` 内部就是 `P=K` 回投 | 决定工作量。原本以为要重做检测，实际一行没改 |
| 缺口 | 没有 `core/pose.py`、没有 `MarkerPose`、`default.yaml` 里既没有 `calibration` 也没有 `pose` 段、没有坐标轴绘制、没有带透视与光照的渲染器 | 决定交付清单，也是排期的依据 |
| 冲突 | 实时入口 `build_live_parser` 的 docstring 写明"不加 `--out`"，而我的计划里正好要给实时入口加落盘开关 | 冲突不解决，写出来就是返工 |

第三张单子最容易被跳过。它要求你读代码的注释和 docstring，而不只是读函数签名。本次就抓到四处冲突：实时入口没有 `--source` 参数（计划里的验收命令不存在）、内参文件在 `.gitignore` 里（新 clone 必然没有）、`assets/aruco` 的图组尺寸是 760×520 到 820×480，而真机内参是 1280×1024（拿真内参跑图组等于自欺）、脚本命名规律是 `check_aruco.py` 而不是 `aruco_pose_check.py`。

读现状还有一个隐性收益：你能提前知道哪些"看起来要做"的事其实是禁的。本仓库明令禁止安装 `opencv-contrib-python`，因为多个包共用 `cv2` 顶层模块会互相覆盖。这类信息不会写在任务书里，只会写在 `progress.md` 的坑表和 `pyproject.toml` 的注释里。

## 三、计划书里必须写死的四样东西

计划书不是把任务书抄一遍。它的作用是让"做完了"这件事可判定。有四样东西必须写死，否则后面每一步都会漂移。

**口径表。** 同一个量，两个人算出不同结果，八成是口径不同。位姿这块要写死的是：码坐标系原点在哪、x/y/z 各指哪、四个模型点的顺序、`tvec` 单位是毫米还是米、`distance` 是斜距还是 z 分量、欧拉角用哪种分解。本次计划书里这六行，后面直接变成了 `docs/interface.md` 的契约条目。

其中"四个模型点的顺序"不是可以自己定的约定，是 `SOLVEPNP_IPPE_SQUARE` 的硬要求。计划书初稿写成了"y 向下"的顺序，复核实测发现同一真值下解出 **距离 3.6 mm、重投影 RMS 5930.682 px**，而正确顺序是 501.3 mm、0.000 px。这个错误在检测环节完全看不出来，ID、四角、中心全对。

**判据。** 每个验收条目要写成命令加期望值，而不是"确认功能正常"。本次的六条长这样：单元测试 11/11、图组逐张核对 28/31、500 mm 处距离误差小于 2%、1000 mm 处小于 3%、全量回归 73 项。数字先按经验定初稿，实测后再定稿，并在文档里注明哪一条被放宽、为什么。

**硬校验。** 计划里要写清"什么情况下必须抛异常"。这一条决定了错误是被挡住还是被静默吞掉。本次定的是两条：重投影 RMS 超过 2.0 px 直接抛 `ValueError`，解出的 `tvec` 的 z 分量小于等于 0 也直接抛。理由是这两类错误的其他输出全部正常，只有这两个数字会露馅。

**交付边界。** 明确写出"缺什么就交付不了什么"。本次写下的是：拿不到相机内参，则距离精度相关的四条验收全部作废，只能交付"链路通了"，不许写任何精度结论。这句话在评审时省掉了一轮扯皮。

### 复核为什么必须用实测，而不是再读一遍

审图的价值在于发现承重墙，而复读自己的计划发现不了承重墙。复核要做的是把计划里的每个可测假设变成一次实际运行。

本次复核写了三个临时脚本，量了 11 条假设，改掉 1 条硬错误、3 条判据错误、4 条与仓库现状冲突的写法。最有代表性的是二义性这一条：计划书原文写"平面位姿在接近正视角时天然二义"，实测结果是正视时两个解完全重合（旋转夹角 0.00°），倾斜时两个解的夹角恰好是倾角的 2 倍（15° 对应 30°、60° 对应 120°），而两个解的距离只差 0.1% 到 0.5%。结论与原计划相反，而且顺带得到一条更有用的判断：**歧义影响的是姿态，几乎不影响距离**。

复核的另一个产出是判据的修正。原计划用"两个解的重投影 RMS 差小于 0.5 px"作为歧义判据，实测发现同一个倾角下这个差值随距离缩小：500 mm 处 0.68 px，1000 mm 处 0.34 px。用绝对像素阈值，远处的码会被误标。改成"相对倍数加旋转夹角"双条件才站得住。

## 四、让数字自己说话

位姿这类任务的特殊性在于，正确与否无法靠肉眼判断。屏幕上画几根坐标轴，歪了 10° 你也不会觉得异常。所以从第一天起就要有真值。

真值的来源只有两条路。手工拍照加卷尺量距离，样本少，只能测单点距离，姿态没有真值。合成渲染，已知旋转和平移，用 `cv2.projectPoints` 把四个角投到图上，再用单应变换把码贴到背景，图与真值一起产出，可以批量刷三十个场景，真值是浮点精确值。本次以后者为主，前者只用于最后的真机抽测。

合成渲染有一个前提必须先验证：**渲染器自己不能错**。做法是把真值 `(R, t)` 和自己投出来的四角喂回解算函数，误差必须是 0。本次 450 mm 场景实测反解误差 0.30%，说明这条链路自洽。

扫描矩阵按单因素设计，一次只动一个维度：

| 维度 | 档位 | 想回答的问题 |
|---|---|---|
| 距离 | 300 / 450 / 675 / 1000 / 1500 / 2000 mm | 多远开始丢，误差怎么涨 |
| 倾角 | 0 / 15 / 30 / 45 / 60 / 75 度 | 教程说"超过 60 度很勉强"在本机是什么位置 |
| 滚转 | 0 / 90 / 180 / 270 度 | 旋转不变性成立不成立 |
| 亮度 | 6 档，含一处真实过曝 | 过曝从哪一档开始丢码 |
| 噪声 | σ = 0 / 8 / 16 | 低照度等效噪声的容忍度 |
| 运动模糊 | 线核长度 0 / 5 / 9 / 13 px | 手抖加长曝光会怎样 |
| 分辨率 | 1280×1024 与 640×480 | 换分辨率不重标定会怎样 |

指标定义里最值得学的是两条。第一条是判定条件要按"物理上可观不客观"来选。倾角在接近正视时不可观：码正对相机时，绕横轴转 10° 只让投影高度缩 1.5%，67 px 的码就差 1 px，与角点定位噪声同量级。本次实测正视档的倾角误差是 4 到 16 度，而一旦倾斜 15 度以上，误差立刻降到 1 度以内。所以工具里对真值倾角小于 10 度的样本只判距离、不判倾角。拿 3 度门槛去卡一个不可观的量，测的是题目本身，不是算法。

第二条是别拿重投影误差当姿态精度。四个点没有冗余，PnP 总能精确穿过这四个点，本次实测 RMS 恒在 0.01 到 0.6 px，误差再大它也不会报警。判断姿态靠不靠得住，看倾角随条件的漂移。

出图有一条硬规矩：一张图只放一个指标。八个指标就是八张 PNG，命名带编号和语义。把距离误差和倾角误差拼进一张 2×2 网格，读的人分不清哪条曲线对应哪个轴，最后谁都不看。

## 五、动手验证

下面这段脚本不涉及相机，也不涉及检测，只复现三类失败模式，确认它们的症状量级。跑一遍几秒钟。目的是让你以后在自己的数据上看到这些数字时，能立刻判断出是哪一类错误。

```python
"""
三种"不报错、只让数字错"的位姿失败模式

用途：复现最容易漏掉的三类错误，量出它们各自的症状量级
输入：无（自己投影合成角点，真值已知）
输出：每种写法的距离与重投影 RMS

跑完应该看到的自检数字：
    正确顺序        d= 501.3 mm  RMS=   0.000 px
    模型点顺序错    d=   3.6 mm  RMS=5930.682 px
    角点交换两点    d=  65.7 mm  RMS= 271.316 px
    内参尺寸不匹配  d=1116.9 mm  偏差 122.8%
"""

import cv2
import numpy as np

L = 40.0
K = np.array([[800.0, 0.0, 640.0], [0.0, 800.0, 512.0], [0.0, 0.0, 1.0]])
D = np.zeros((1, 5))
rvec = np.array([0.30, -0.20, 0.10])
tvec = np.array([30.0, -20.0, 500.0])


def solve(obj, img, K_use):
    _ok, r, t = cv2.solvePnP(obj, img, K_use, D, flags=cv2.SOLVEPNP_IPPE_SQUARE)
    proj, _ = cv2.projectPoints(obj, r, t, K_use, D)
    rms = float(np.sqrt(np.mean(np.sum((img - proj.reshape(-1, 2)) ** 2, axis=1))))
    return float(np.linalg.norm(t)), rms


# ==== 1. 正确的模型点顺序：IPPE_SQUARE 的硬要求，对应图像 TL/TR/BR/BL ====
obj = np.array([[-L / 2, L / 2, 0], [L / 2, L / 2, 0], [L / 2, -L / 2, 0], [-L / 2, -L / 2, 0]])
img, _ = cv2.projectPoints(obj, rvec, tvec, K, D)
img = img.reshape(4, 2)
d0, rms0 = solve(obj, img, K)
print(f"正确顺序        d={d0:7.1f} mm  RMS={rms0:8.3f} px")

# ==== 2. 把顺序写成"y 向下"那套：看起来合理，实际把四角配成蝴蝶结 ====
obj_bad = np.array([[-L / 2, -L / 2, 0], [L / 2, -L / 2, 0], [L / 2, L / 2, 0], [-L / 2, L / 2, 0]])
d, rms = solve(obj_bad, img, K)
print(f"模型点顺序错    d={d:7.1f} mm  RMS={rms:8.3f} px")

# ==== 3. 交换相邻两个角点：检测结果照样是四个点，但配对错了 ====
d, rms = solve(obj, img[[1, 0, 2, 3]], K)
print(f"角点交换两点    d={d:7.1f} mm  RMS={rms:8.3f} px")

# ==== 4. 内参尺寸不匹配：640x480 的内参套到 1280x1024 的图上 ====
K_small = K.copy()
K_small[0, :] *= 0.5
K_small[1, :] *= 0.5
img_small, _ = cv2.projectPoints(obj, rvec, tvec, K_small, D)
d, rms = solve(obj, img_small.reshape(4, 2), K)   # 用大尺寸的 K 解小尺寸的图
print(f"内参尺寸不匹配  d={d:7.1f} mm  偏差 {(d / 501.3 - 1) * 100:5.1f}%")
```

预期输出（本机实测）：

```text
正确顺序        d=  501.3 mm  RMS=   0.000 px
模型点顺序错    d=    3.6 mm  RMS=5930.682 px
角点交换两点    d=   65.7 mm  RMS= 271.316 px
内参尺寸不匹配  d= 1116.9 mm  偏差 122.8%
```

### 怎么确认自己跑对了

1. 第一行必须是 `501.3` 和 `0.000`。写成 500.0 说明你把真值当成了结果，没走解算。
2. 第二行的 RMS 必须是四位数。如果只有几十像素，说明你交换的是两个对角的点，而不是把整串顺序反过来，这两种错法的症状量级不同。
3. 第三行的距离必须明显小于真值。距离变小的直觉是：配对错误让四个点被解释成一个更小的正方形，于是"更远"变成"更近"。
4. 第四行的偏差必须是正数且超过 100%。如果接近 0，说明你忘了把小尺寸的内参乘 0.5，两次用的是同一套内参。

## 七、做这件事之前要避开的坑

**症状是"数字变小"而不是"报错"，先查单位与顺序。** 位姿里所有配对错误都表现为距离变成原值的某个奇怪比例，3.6 mm、65.7 mm、1116.9 mm 都是本次实测的真实数字。报错反而是好事，说明参数校验拦住了。

**重投影误差小不代表结果对。** 四个点没有冗余，任何四组点都能被某个位姿精确穿过。本次实测倾角错 25 度时 RMS 只有 0.5 px。判断姿态要看倾角随条件漂移，别看 RMS。

**拿"乘一个系数"模拟过曝等于没测。** 把图像乘 2.2，黑框乘完还是 0、白格乘完仍是 255，对比度一点没丢，五档全过。真实过曝是环境光把黑框照亮、增益把白格截顶，必须写成"先加环境光再乘增益"。本次改成 3.0 倍加 110 环境光，才真的丢码。

**分辨率变了不重标定，误差翻倍还找不到原因。** 1280×1024 的内参直接套 640×480 的图，等效换了一颗长焦镜头，本次实测距离偏 122.8%。工具里必须按宽高比缩放 `fx/cx` 与 `fy/cy`，而且要在内参与图像尺寸不一致时打日志。

**去畸变的两种口径混用，偏得不多但一直偏。** 角点已经 `undistortPoints` 掰直后，PnP 再传畸变系数就是去畸变两次。本次实测画面中心偏 0.62%，码偏到边缘时偏 14.6%。两种口径必须成对出现，代码里要么都不传，要么都在一处处理。

**验收命令要照着 `--help` 写，不要照着记忆写。** 本次计划里的 `run_aruco_live --source camera` 这个参数并不存在，实际是 `--set input.source=camera`。这类错误在评审时最伤信任，因为它看起来像是没跑过。

## 附：把这套工作流套到下一个任务

下一个任务大概率是 ROS 2 节点对接。同一个骨架，换掉内容：

| 步骤 | 位姿估计任务里的做法 | ROS 2 对接时对应做什么 |
|---|---|---|
| 读现状 | 比对分支、读契约、找可复用件 | 读 `cli/` 的退出码与日志约定、读现有消息字段 |
| 三张单子 | 可复用 / 缺口 / 冲突 | 冲突重点查话题名由谁定、`core` 层是否被允许 import `rclpy` |
| 写死口径 | 坐标系、单位、四角顺序 | 话题名、消息字段、时间戳来源、坐标系 `frame_id` |
| 复核 | 三个临时脚本量 11 条假设 | 用 `ros2 topic echo` 抓一帧真实消息，别凭文档写字段 |
| 分层实现 | `core/pose.py` 纯算法，`cli` 编排 | 算法留在 `core`，节点只做转换与发布 |
| 判据 | 11 项单测加四条精度条目 | 发布频率、消息字段齐全、断连不崩、`colcon test` |
| 文档 | 契约、原理、坑表 | `interface.md` 加消息段，`progress.md` 记新坑 |

写代码时用得上的关键接口，只给形状不给实现：

| 要做的事 | 关键 API |
|---|---|
| 用四个共面点解位姿 | `cv2.solvePnP(obj_pts, img_pts, K, D, flags=cv2.SOLVEPNP_IPPE_SQUARE)` |
| 拿两个候选解做歧义诊断 | `cv2.solvePnPGeneric(...)` 返回 `(个数, rvecs, tvecs, 误差)` |
| 把真值投成四角像素 | `cv2.projectPoints(obj_pts, rvec, tvec, K, D)` |
| 旋转向量与矩阵互转 | `cv2.Rodrigues(rvec)` |
| 归一化角点后求解 | `cv2.undistortPoints(pts, K, D, P=K)`，此时 PnP 传 `D=None` |
| 按新分辨率缩放内参 | `fx/cx` 乘宽比、`fy/cy` 乘高比，畸变系数不缩放 |
