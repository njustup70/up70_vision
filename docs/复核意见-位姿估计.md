## 四、必修（阻塞合入）

### P1-1 IPPE_SQUARE 返回 NaN 时，兜底逻辑不触发

**现象**：严格正视、严格居中的完美方形，`cv2.solvePnPGeneric` 的两个候选解**全是 NaN**，
兜底分支不执行，最终从 `MarkerPose.__post_init__` 抛出一个**原因写错**的 `ValueError`。

**证据**（`PoseSpec(300 mm, tilt=0, 23 mm)` 渲染 + 检测）：

```text
solution_count=2  errs=[nan, nan]
sol0: rvec=[nan, nan, nan] tvec=[nan, nan, nan]
ITERATIVE ok=True tvec=[0.0, -0.0, 302.48]      <- 兜底本来能解，但没被调用
```

```text
ValueError: tvec_mm[2] 必须为正（码在相机前方），收到 t=[nan, nan, nan]；
常见原因是角点顺序与模型的点顺序对不上
```

**根因**（两处，都在 `core/pose.py`）：

```python
# core/pose.py:192-203
def _score_candidates(candidates, object_points, corners, matrix, dist_coeffs) -> list:
    """给每个候选解算重投影 RMS，并扔掉"解到相机后方"的。"""
    scored = []
    for rvec, tvec in candidates:
        if tvec[2] <= 0:                       # NaN 不满足 <= 0，没被拦
            continue
        rms = _reproject_rms(...)              # 这里也是 NaN
        scored.append((rms, rvec, tvec))
```

```python
# core/pose.py:286-288
    scored = _score_candidates(...)
    used_fallback = False
    if method == "ippe_square" and (not scored or scored[0][0] > limit):
```

- `nan > 2.0` 恒为 **False** → 兜底永不触发；
- 判据用的是**排序前**的 `scored[0]`，不是最小 RMS（即使不 NaN，也不该这么写）。

**影响**：批量工具撞到一个严格正视样本就中断整批（`pose_sweep` / `pose_check` 都是整批失败），
而「500 mm 正视」正是计划书 S4 的验收场景；报错文本还会把人引向「角点顺序」，
与 `docs/位姿估计.md` 第五节「已用 ITERATIVE 兜底」的说法直接矛盾。

> **作者更正（2026-10-18，已复跑）**：影响面这一段不成立。`pose_check.check_one` 在
> `except ValueError` 里把单张失败折成一条 `reason`（源码第 133 行），`cli` 也是逐码 try 的。
> 用 23 mm + 合成内参实测：批量照跑完，只有 `dist_0300` 一张标「解算失败」，结果 24/31。
> 所以是**单张误诊**而不是整批中断，严重度应从 P1 降到 P2。
> 根因也比本文更靠前一步：同一张图用 float32 角点调 `_raw_candidates` 得到
> `rms=0.0100 / t=[0.0, -0.0, 302.48]`，经 `_check_corners` 转成 float64 后才退化成 NaN。

**建议改法**：`_score_candidates` 里 `if not np.isfinite(rms): continue`；兜底判据改成
`best = min((item[0] for item in scored), default=inf)` 后比较 `best > limit`。

### P1-2 Windows 控制台下工具跑不完，「退出码 0」判据不成立

**现象**：`pose_check` / `pose_sweep` / `run_aruco_live` 打印 `✅ / ⚠️ / ❌` 时抛
`UnicodeEncodeError: 'gbk' codec can't encode character`，进程 `exit 1`。

**证据**：

```text
File "src\up70_vision\tools\pose_check.py", line 260, in main
    print(f"{record['image']:<22}...{'⚠️ ' + record['reason']}")
UnicodeEncodeError: 'gbk' codec can't encode character '\u26a0'
```

```text
File "src\up70_vision\cli.py", line 816, in run_aruco_live
    print("✅ 运行成功")
UnicodeEncodeError: 'gbk' codec can't encode character '\u2705'
```

**归因**：`cli.py` 那条是 `main` 上既有问题（`#7` 引入），不属于本次改动；
但**新工具沿用了同一写法**，而 S7 的验收判据是「退出码 0」，所以在本机验收前必须先设
`PYTHONIOENCODING=utf-8`，否则判据无法成立。容器（Ubuntu，UTF-8）无此问题。

**建议改法**：`scripts/*.py` 入口统一 `sys.stdout.reconfigure(encoding="utf-8")`；
或把 `✅/⚠️/❌` 换成 ASCII（`[OK] / [!] / [x]`）——后者与「图上文字一律 ASCII」的既有约定更一致。

## 五、应修（不报错、只让判断失效）

### P2-1 三个配置字段是死的，`--set` 静默无效

`pose.ambiguity_ratio`、`pose.ambiguity_deg`、`pose.max_tilt_deg` 在 `schema.py` 有字段、
有校验、有参数速查表，`default.yaml` 还写了「超过只在日志里提示」，但**全仓只有 `schema.py` 引用它们**：

```python
# config/schema.py:331-334
    ambiguity_ratio: float = 3.0
    ambiguity_deg: float = 10.0
    max_tilt_deg: float = 75.0
    max_reproj_rms_px: float = 2.0
```

`core/pose.py` 实际用的是模块常量（`AMBIGUITY_RATIO = 3.0`、`AMBIGUITY_DEG = 10.0`），
`max_tilt_deg` 连日志提示都没实现。

**影响**：`--set pose.ambiguity_deg=20` 改了配置、校验通过、结果不变——正是 `interface.md` §5
「配置字段是契约，改名会让 `--set` 静默失效」要防的反面。

**建议**：二者取一，不要留中间态。① `solve_pose` / `estimate_pose` / `estimate_poses` 增加
`ambiguity_ratio` / `ambiguity_deg` 形参，`cli` 与 `tools` 从配置传入；`max_tilt_deg` 在
`cli` 里按 `pose.tilt_deg > cfg.pose.max_tilt_deg` 打一行提示。② 或从 `default.yaml`、
`schema.py`、参数速查表里删掉，等真要用时再加。

### P2-2 `pose.marker_size_mm` 默认值 40.0 是个静默 74% 误差陷阱

实测边长是 **23 mm**（`progress.md` 坑 40：打印机把 15 mm 打成 23 mm），
`configs/default.yaml` 仍留 `40.0` 占位。README 的命令都带了 `--set pose.marker_size_mm=23`，
所以照文档走不会错；但任何人只写 `--set pose.enabled=true` 就会拿到**距离整体偏 +74%**
且重投影 RMS 完全正常的结果——与坑 40 的失败模式一模一样。

**建议**：默认值改成 `23.0`（仓库已有实测值），注释保留「换码就要重量」；
或把 `marker_size_mm` 设成必填（缺省时 `ConfigError`，像 `calibrate_camera.py` 的 `--square-mm` 那样）。

### P2-3 `pose_check --intrinsics` 无条件下压真值里的 K，且不告警

`tools/pose_check.py` 只要给了 `--intrinsics` 就用它，**忽略真值 JSON 自带的 `camera_matrix`**；
只有「画布尺寸不同」时才警告，K 本身不对时一声不吭。

**证据**（拿合成 K 的旧图组 + 真机 K）：

```text
python scripts/pose_check.py --dir output/pose_scenes --intrinsics configs/camera_calibration.yaml --marker-mm 23
-> 通过 0/31，31 张距离全部偏 65.8%（fx 1321 vs 800），退出码 1
```

**根因**：`output/pose_scenes`（合成 K、40 mm）与 `output/pose_scenes_real`（真机 K、23 mm）
只差一个后缀，README 那两条命令必须**连着跑**；单跑第二条就会命中错目录。

**建议**：真值里含 `camera_matrix` 且 `fx` 相对差 > 5% 时，打印警告并**优先用真值 K**
（真值 K 是渲染这批图时真正用的那套）；顺带在目录名或 README 上把两组图区分开。

### P2-4 噪声档跨进程不可复现

```python
# tools/gen_pose_scenes.py:288
        rng = np.random.default_rng(abs(hash(spec.name)) % (2 ** 32))
```

Python 的字符串 `hash()` 每进程随机（`PYTHONHASHSEED` 未固定）。三次独立运行同一场景名得到
`40350 / 30148 / 54421`，即 `noise_08` / `noise_16` 两档每次的噪声图都不同。

**影响**：与计划书 3.1「每档可重复」相反；这两档的误差数字会在小范围内抖动，
不适合当回归基线。

**建议**：`zlib.crc32(spec.name.encode("utf-8"))` 或把 `seed` 写进 `PoseSpec`（显式优于隐式）。

## 八、关于「测试是否需要相机」

**位姿估计不需要相机。** 复核时在**无相机**条件下完整跑通了：
合成图自洽、回放实时链路（`--source replay` 出 `d/tilt/yaw` + 坐标轴）、31 场景扫描、

需要相机的只有三件事，且都是**结论强度**问题，不是代码能不能跑：

| 事项 | 现状 | 没有相机的后果 |
|---|---|---|
| S2b / S9 真机精度抽测（距离 vs 卷尺） | 未做，文档已标「未验证」 | 只能写「解算链路通了」，不能写「场上距离误差 X%」 |
| 真实畸变下的坐标轴对齐 | 用 `dist=None` 画在畸变图上 | 画面边缘若干像素错位，只有实拍看得出 |
| 任务单第 3 条「识别效果测试」的可信结论 | 纯合成 | 合成 = **识别能力上限**（无压缩噪声、边缘理想）；实拍的模糊、反光、运动模糊分布都不同，「每格 2.5 px 可检」不能搬上场 |

**低成本替代**（没有工业相机也能补）：手机拍 20–30 张（不同距离/角度/光照），卷尺量 3 个距离，
放进 `data/pose/real`，跑

```bash
python scripts/pose_check.py --dir data/pose/real \
    --intrinsics <手机标定或近似内参> --marker-mm 23
```

这样 S9 能从「未验证」变成「手机抽测」，比空着强；仍不能替代工业相机下的结论。

## 十一、作者反馈（2026-10-18）

复核的 6 条 P1/P2 与 4 条 P3 已按第十节回填处理。以下三条**没有照办**，理由与证据如下。

### 11.1 P3-1「13 条正文全空」不成立

`git log --format=%B` 实测 9 条有正文，4 条空（3 条 docs 合规、1 条 fix 待补）。已在该节插入更正说明，详见 §六。

### 11.2 P1-1 不会「中断整批」

`pose_check.check_one` 与 `cli` 都有逐样本 try/except，实测批量照跑完。严重度按单张误诊处理（P2），
但根因（NaN 绕过所有比较校验）确实要修，已修并加回归用例。

### 11.3 P2-3 不做「优先用真值 K」

`--intrinsics` 是显式参数。静默改用真值 K 会让「我想试另一套内参」变得不可能，也会让
`--intrinsics` 在某些情况下变成摆设。改成**告警但不覆盖**：

```text
⚠️  内参 fx 与真值不一致：你给 1321.0，真值是 800.0（差 65.1%）；继续用你给的那套，距离会整体偏
```

同时 `docs/progress.md` 记了这条坑（第 51 条同族）：换分辨率/换内参时先看这条告警。

### 11.4 另外两条口径说明

- P1-2 归为 P2：团队标准运行环境是 Ubuntu 22.04 容器（UTF-8），Windows 原生不在支持范围内；
  崩溃属真，但没有到「阻塞合入」。已用 `utils/console.ensure_utf8_stdout()` 修掉，
  且保留 `✅/⚠️` 与仓库既有工具一致。
- P3-7 的「cv2 导入与其他 core 模块不一致」作为论据不成立：`calibration.py` 4 处、
  `aruco.py` 5 处、`pipeline.py` 1 处都是函数内 import，`pose.py` 跟的是这一批；
  只有 `color.py` / `blob.py` 是顶层。已补一行说明「为什么」，代码不动。
