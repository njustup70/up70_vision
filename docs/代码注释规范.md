# 代码注释规范（v1，2026-10-17）

> 适用范围：`src/`、`configs/`、`tests/` 里的注释与 docstring。
> 来源：任务二的 `cli.run_aruco_live()` 与 `detectors/stub_aruco.py` 按两轮反馈定稿，
> 这一档作为团队标准；以后新增代码照此写，存量代码改到哪补到哪。
> 一句话：**先用大白话把工作流讲明白，再给技术细节**；注释回答「是什么、为什么这样做、不这样会怎样」，
> 不是把代码翻译成中文。

---

## 1. 底线（三条，缺一条不算写完）

1. **每个模块、每个类、每个函数（含 `_private`）都要有 docstring。**
2. **每个类属性 / 配置字段都要说明**：它代表什么、单位或取值范围、谁在用它。
3. **注释与代码在同一次提交里改。** 过期注释比没有注释更糟——它会把下一个人引到错的地方。

不合格的注释（复述代码，零信息量）：

```python
i += 1          # i 加一
return markers  # 返回 markers
```

合格的注释（说清意图与边界）：

```python
# 帧号先记下再自增：无码分支提前返回时也必须算"过了一帧"，
# 否则 empty_after 会一直等不到第 N 帧（不报错，只是永远不清空）
index = self.frame_count
self.frame_count += 1
```

## 2. 四层结构

| 层级 | 写在哪 | 必须包含 | 长度参考 |
|---|---|---|---|
| 模块 | 文件开头 `"""..."""` | **「用大白话说」这一段**（这个文件在干什么）、职责、放什么/不放什么、依赖方向、对外约定（返回值/空值/退出码）、已知的坑 | 10~35 行 |
| 类 | `class` 下 docstring | **「用大白话说」**、属性清单（名字/类型/含义）、不变量、配置速查表、用法示例 | 5~25 行 |
| 函数/方法 | `def` 下 docstring | **「用大白话说」**（这一步在干嘛）、一句话职责、`:param:` / `:return:` / `:raises:`、副作用、例子；复杂算法再加步骤与公式 | 5~35 行 |
| 语句/分支 | 行内 `#` | **人话版"这一步在干嘛"** + 为什么、边界条件、写错的症状 | 一行，必要时两行 |

判断标准：**没参与实现的人只看注释，能顺着"取一帧 -> 找码 -> 画图 -> 输出"说出整条工作流；要改代码的人能明白"为什么不是另一种写法"。**

> 「长度参考」是写清楚时的参考**上限**，不是目标。要不要写只问一句：删掉这段，接手的人会不会多踩一次坑？会就留，不会就删。
>
> 密度参考（本仓库实测）：教学件 `stub_aruco.py` 67%、流程代码 `cli/live.py` 47%、配置 `schema.py` 24%。
> 比例随文件规模变化：只有十几行真实代码的小模块，四层齐全时 60% 以上很正常；几百行的流程代码通常 40%~50%。
> 所以别拿比例当验收标准，只拿它做横向对照。往高走的是算法、公共 API、踩过坑的地方；往低走的是纯转发、一眼能懂的配置。

### 2.1 通俗性：先讲人话，再讲细节

**防的是**：注释全是术语和缩写，只有写代码的人看得懂 —— 换个人接手只能重读实现。

**怎么做**

1. **每个模块、每个类、每个关键函数，docstring 第一段固定叫「用大白话说」**，3~6 行，
   用主谓宾短句，不用缩写、不堆名词。例如：
   ```python
   """实时循环：读帧 -> 检测 -> 绘制 -> 显示/落盘 -> 等键。

   用大白话说
       打开相机（或回放/合成图），一帧一帧地拿：每拿一帧就找一次码，
       在画面上把码框出来，显示到窗口（或存成图片），顺手在终端报一句
       "现在有几个码、分别在哪"。码移动、转动、多出几个，下一帧就按新结果重画。
   """
   ```
2. **给一个能"跟着走一遍"的例子**：具体帧号、具体数字、真实输出行。
   ```text
   第 1 帧：检测到 2 个码 -> 画框 -> 终端打一行
            t=0.03s frames=1 fps=30.2 markers=2 | id=3 center=(320.0, 240.0)
   第 90 帧：id=7 移出画面 -> 终端立刻补一行 markers=1
   ```
3. **术语/缩写第一次出现时给一句解释**（如"fps：每秒处理几帧"），不要假设读者知道。
4. **行内注释也先说人话**，再补技术原因：
   ```python
   # 人话：先把"找码的工具"准备好，再去开相机。
   # 技术：相机是独占资源，检测器建不起来时不该先占住相机。
   ```
5. **通俗不等于含糊。** 不能写"处理一下数据""做一些判断"；单位、取值范围、空值语义、
   异常/退出码仍然必须写清。比喻只用来帮助理解，**不能替代技术定义**。

### 2.2 完整例子：一个文件里的四层注释

下面是个虚构文件 `vision/core/fps.py`（只用来示范写法，仓库里没有）。选帧率统计是因为
几乎每个视觉项目都要用：有状态、有边界、有坑，又不涉及算法。

全文 69 行：真实代码 17 行、注释 43 行（62%）。小模块的比例天然高，这不代表它就是目标密度；
判断标准仍是上一节那句——删掉会不会让人多踩一次坑。

```python
"""统计实时循环的帧率（FPS）。

用大白话说
    每处理完一帧调一次 tick()，这里记下时间，算出"每秒几帧"。

放什么：纯计数，只依赖时间戳。
不放什么：打印在 cli/，画图在 viz/，超阈值怎么处理由调用方定。

对外约定
    tick() 返回 float；不足两帧返回 0.0（不是 None，省得调用方到处判空）。

已知的坑
    time.time() 会被系统校时影响，可能算出负帧率；这里用 perf_counter()。
"""

from __future__ import annotations

import time


class FpsMeter:
    """滑动窗口帧率统计。

    用大白话说
        只记最近 N 帧的时间戳，用首尾间隔算平均帧率；窗口越大越稳、也越迟钝。

    属性
        window: 参与统计的帧数，默认 30（30fps 下约 1 秒）。
        _stamps: 最近 N 次 tick 的时间戳（秒），单调递增。
    """

    def __init__(self, window: int = 30) -> None:
        # 配置里 0 通常表示"不统计"，统一当 1，顺便避免后面除以 0
        self.window = max(1, int(window))
        self._stamps: list[float] = []

    def tick(self, now: float | None = None) -> float:
        """记一帧，返回当前帧率。

        用大白话说
            每帧调一次，把时间记进窗口，再用首尾两个时间戳的差除以间隔数，
            就是这段时间的平均帧率。

        :param now: 时间戳（秒）；None 表示自己取 perf_counter()
        :return: 帧率（帧/秒）；不足两帧、或间隔为 0 时返回 0.0

        副作用
            改内部时间戳列表；不是线程安全的。

        例子
            >>> m = FpsMeter(window=5)
            >>> m.tick(0.0), m.tick(0.1)
            (0.0, 10.0)
        """
        now = time.perf_counter() if now is None else float(now)
        self._stamps.append(now)

        # 只留最近 window 个：多了从头删，否则窗口越滚越大、数字越来越钝
        if len(self._stamps) > self.window:
            del self._stamps[0]

        # 边界：只有一个时间戳算不出间隔，返回 0.0 而不是抛异常
        if len(self._stamps) < 2:
            return 0.0

        span = self._stamps[-1] - self._stamps[0]
        if span <= 0.0:          # 测试里连调两次、或时钟异常时会撞上
            return 0.0
        return (len(self._stamps) - 1) / span
```

对照着看：

- 模块头：先讲"算什么、不算什么"，再给对外约定和已知的坑，不罗列实现细节。
- 类：大白话 + 属性表；用法示例不重复写——下面的函数例子已经示范过一次。
- 函数：`:param:` 说清 None 的含义，`:return:` 说清 0.0 的语义（不是"失败"），副作用一句话。
- 行内：只写边界（不足两帧、间隔为 0）和为什么（窗口要裁剪），没有一行复述代码。

复杂算法才需要编号步骤、公式和 ASCII 图（见 §5.3）。这个例子故意不凑——**该密的密，该省的白省**。

## 3. 模块头怎么写

模板：

```python
"""<一句话职责>。

放什么 / 不放什么
    <这个模块该承担的、不该承担的；越界的代码应该去哪>

依赖谁 / 被谁用
    <只依赖 X，不 import Y，避免循环依赖；上层是 Z>

对外约定
    <返回值结构、无目标时返回什么、异常/退出码、形参名是否算契约>

已知的坑
    <现象 + 原因 + 处理，编号指向 docs/progress.md 第五节>
"""
```

要求：

- **多入口/多流程的模块给对照表**，否则读者分不清什么时候用哪个（见 `cli/` 的 `run()` / `run_aruco_live()`）。
- **契约原文不在注释里抄一遍**，写清"哪一条"并指向 `docs/interface.md`，避免两处漂移。
- 坑只写结论和编号，详细过程留在 `progress.md`。

## 4. 类怎么写

```python
class StubArucoDetector(Detector):
    """按契约伪造 ArUco 码的检测器（无模型、无相机也能跑通链路）。

    属性（构造时定型，之后只读；frame_count 除外，每调一次 detect 加 1）
        name (str)           检测器名，工厂用它对齐配置里的 detector.name
        ids (list[int])      要伪造的码 ID，列表顺序 = 画面里从左到右的顺序
        frame_count (int)    已调用 detect 的次数，既是"当前帧号"也是运动相位来源
    """
```

- 属性表里的"谁在用/会不会变"比类型更重要：只读属性被误改，往往不会立刻报错。
- 有取值范围/默认值的（配置类、检测器参数），给一张**参数速查表**：键 / 类型 / 合法值 / 默认值。
- 有不变量的，单独写一句（例：`center_px` 恒等于四角算术平均）。

## 5. 函数怎么写

### 5.1 基本模板

```python
def run_aruco_live(argv=None) -> int:
    """一句话职责（动宾结构）。

    与 xxx 的区别
        <同名/相似函数之间怎么选；写错会得到什么错误现象>

    :param argv: 参数含义 + 取值约定（None 表示什么）
    :return: 返回值语义；多种取值逐个列（0 成功 / 1 结果不可用 / 2 没跑起来）
    :raises <异常类型>: 什么情况下抛（调用方能否处理）
    副作用
        读文件 / 开窗口 / 占用设备 / 写磁盘——调用方需要知道的都写
    例子
        <一条能直接复制的命令或调用>
    """
```

### 5.2 必须写清楚的五类信息

| 信息 | 为什么必须写 | 示例 |
|---|---|---|
| 参数的含义与取值 | 光看类型看不出 `side_px` 是边长还是半边长 | `:param side_px: 码边长（像素）` |
| 返回值的各种情况 | `[]` / `None` / `(结果, 状态)` 分不清就会出现分支漏判 | `无码返回 []，不是 None` |
| 异常与退出码 | 上层要决定"重试还是退出" | `0 成功 / 1 结果不可用 / 2 没跑起来` |
| 副作用 | 相机是独占资源，忘了 close 下次打不开 | `占用设备，必须 close()` |
| 为什么不用另一种写法 | 防止后人"优化"掉关键逻辑 | `不用 time.time()：它会被系统时钟调整影响` |

### 5.3 复杂算法：编号步骤 + 公式 + 示意图

一个函数里超过 5 个逻辑步骤，或涉及坐标/几何/统计时，按步骤编号注释，并给出公式或图：

```python
# ---- 步骤 1：帧号先记下再自增 ----
# ---- 步骤 2：无码模式直接返回空列表 ----
...
# 极坐标 → 直角坐标：cx = cx0 + r·cosθ，cy = cy0 + r·sinθ
```

几何/版面/状态流转用 ASCII 图（图内文字一律 ASCII）：

```
(-h,-h) TL ─────── TR (h,-h)      ① 以中心为原点摆好轴对齐正方形
        │    ↑    │                ② 绕原点旋转 spin_deg
        │  中心   │                ③ 平移到 (cx, cy)
(-h, h) BL ─────── BR (h, h)
```

## 6. 行内注释：只写三类

| 类型 | 写什么 | 例子 |
|---|---|---|
| **为什么** | 选择这个写法的理由、取舍、被否掉的替代方案 | `用 OSError 覆盖 FileNotFoundError / IOError（回放目录不存在、视频打不开等）` |
| **边界** | 0 / None / 空列表 / 负数 / 并发时怎么处理 | `None / "" 都当作 0（不启用）` |
| **症状** | 写错之后会看到什么（尤其是"不报错但结果不对"） | `不查这个属性，imshow 会不停重建窗口` |

不写：

- 复述语句（`# 自增`、`# 返回结果`）；
- 显而易见的类型说明（`# int`）；
- "TODO：优化"这种没有对象和条件的备忘——要么写清条件和原因，要么提 issue。

魔法数字必须写来源（几何关系 / 实测取值 / 经验值 + 测量条件）：

```python
gap = self.side_px * 1.6    # 中心距 = 1.6 倍边长：留 0.6 条边的空隙，旋转时不互相压住
```

## 7. 特殊场景

**argparse 参数**：每个参数一行注释，写清"作用 + 默认 + 为什么要有它"。多个入口共用的参数抽成一个函数，注释写在共用处。

**配置校验**：报错信息必须带字段路径、当前值、合法值；注释写清"写错的症状"（例：`mode` 只接受 normal/none，写错会在配置阶段报，而不是跑起来才发现）。

**异常处理**：每个 `except` 说明捕获什么、为什么捕获、捕获后调用方看到什么。禁止裸 `except:`。

**性能相关数字**：写实测值和测量条件（分辨率、机器），不要写"很快"；大段实测数据进 `docs/progress.md`，注释里只留结论 + 条件，或指向 `progress.md` 对应条目。

**tests/ 下的测试函数**：docstring 一行就够——写"测什么 + 期望结果"（例：`"""空图返回 None，不抛异常。"""`），不要求「用大白话说」段落和 `:param:` / `:return:`。测试靠用例名和断言里的具体数字让人看懂。

**图上的文字**：一律 ASCII。`cv2.putText` 的 Hershey 字体不含汉字字形，传中文会画问号且不报错（`progress.md` 坑 11）。

## 8. 提交前自检（7 条）

- [ ] 新增的模块/类/函数都有 docstring，函数带 `:param:` / `:return:`（有异常/副作用的补 `:raises:`/副作用；测试函数一行即可）
- [ ] 模块、类、关键函数都有「用大白话说」段落，并给了能跟着走一遍的具体例子；**没参与实现的人只看注释能说出工作流**
- [ ] 新增的配置字段能在类文档或速查表里找到"是什么、取值、谁在用"；复杂函数按步骤编号，关键推导有公式或 ASCII 图
- [ ] 每个魔法数字都有来源，每个 `except` 都有理由
- [ ] 注释与代码一致（改了逻辑，注释同步改）
- [ ] 没有复述代码的注释；没有过期注释
- [ ] 图/终端输出里的文字是 ASCII

## 9. 参考实现

规范只说「要写什么」，不说「写到什么程度」。不确定时对照这三个**真实文件**——
它们各自把某一类代码写到了标准以上，按你正在写的那一类对号入座：

| 文件 | 突出的特点（为什么拿它当样板） | 具体看哪 |
|---|---|---|
| `vision/cli/live.py` | 注释跟着运行时序走：读一遍就能在脑子里把进程跑起来 | 模块头的多入口对照；`run_aruco_live()` 里「第 1 帧 / 第 90 帧 / 按 q 退出」的走查例子；启动步骤与主循环的分段；常量的取值理由 |
| `vision/detectors/stub_aruco.py` | 把"假实现"讲到外人也能验收：契约、版面、帧号规则全部写死 | 模块头的契约清单和"每帧必须调一次"的坑；类文档里的版面 ASCII 图；`_marker()` 的旋转/平移分步与公式 |
| `vision/config/schema.py` | 报错信息本身就是文档：写错时直接告诉你哪个字段、错在哪、合法值是什么 | `DetectorConfig` 的参数速查表；`validate()` 的校验清单与"为什么在构造期就报错" |

一句话选法：写流程看 `cli/live.py`，写算法或类看 `stub_aruco.py`，写配置或校验看 `schema.py`。

> 与 `docs/视觉组协作规范.md` 的关系：那边管"怎么提交、怎么评审、AI 生成的代码要能解释"，
> 这边管"注释写到什么程度"。两边冲突时，以协作规范的流程为准、本文件的注释要求为下限。
